# 流式交付与首字延迟

## 参考与边界

参考本地 ZCode 的 `apps/zcode-cli/packages/bootstrap/src/zcode-protocol/server-operations.ts`：
首个正文、思考增量优先交付，后续增量可以合并；控制事件和终态必须保持顺序。
ZCode 桌面使用 stdio，K-brain 使用 HTTP SSE，不复制其传输协议或业务状态。

K-brain 是执行和事件序号的唯一所有者。LiveAgent 发起运行，收到接受结果后按
`accepted_seq` 订阅事件；重连使用最后收到的序号继续读取。聊天显示不等待运行完成，
不通过轮询完整历史实现流式输出。会话日志仍先于事件对外可见，不改为易丢失的旁路。

```text
LiveAgent             K-brain                  模型供应商
    | POST run           |                         |
    |<-- accepted_seq ---|                         |
    | GET events         |---- streaming request ->|
    |<-- SSE headers ----|                         |
    |                    |<-- thinking/text delta -|
    |<-- first delta ----|                         |
    | update transcript  |<-- more deltas ---------|
    |<-- ordered events -|                         |
    |<-- terminal -------|                         |
```

## 交付规则

- SSE 响应立即刷新头部，设置 `X-Accel-Buffering: no` 和 `no-transform`，避免支持
  这些头部的反向代理缓存完整回答。自定义代理仍需自行正确配置流式转发。
- 正文和思考各自的首个增量立即刷新，不等待同批历史事件全部写完。
- 长批次最多每 32 个事件刷新一次；每批结束和终态仍刷新，保持有限批量开销。
- 事件序号、重放内容、鉴权、取消及终态语义保持不变。

## 验收

- 检查 SSE 头部立即可用、禁止代理缓冲。
- 已有事件重放中，首个思考、正文增量各自位于刷新边界。
- 大批事件分段刷新，所有序号连续，终态最后交付；从游标恢复不重发旧事件。
- 模型先发一个增量并等待外部释放时，客户端在模型完成前能读到该增量。

这些规则只减少传输等待，不证明生产环境首字延迟由 SSE 缓冲造成。供应商排队、
推理、历史压缩、钩子及请求准备仍需结合实际请求计时定位。

## 本地验证记录

- 两项交付回归使用竞态检测连续执行三次通过；后端整包测试和 `go vet` 通过。
- Chrome 使用 LiveAgent `beta.18` 的真实 `runKBrainTurn`、聊天状态控制器和
  `ChatTranscript`，连接本次构建的真实 K-brain。仅模型供应商使用可控响应。
- 1280×850 和 390×850 下，首段显示时运行仍为进行中；释放模型等待后，后段
  按顺序追加，运行正常完成，均无页面异常。
- 从 fixture 发送到首个正文回调约为 26.1 / 25.8 毫秒。这是本地固定响应链路
  验证，不是生产模型首字性能，也不是相对旧版本的加速比。
- LiveAgent 无需更换传输协议。其现有首段立即更新、后续按帧批处理逻辑保留。
