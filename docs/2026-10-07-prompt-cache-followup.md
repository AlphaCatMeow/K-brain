# 2026-10-07 请求前缀与真实缓存复核

## 修复

- todowrite 不再向每次请求末尾添加下一轮会消失的 system 消息。
- 新计划随工具结果持久化；已有同一计划时不重复添加。
- 恢复旧计划或压缩丢失工具结果时，用用户消息的 `prompt_context` 保存请求专用快照。
- 后台记忆索引按变化追加快照，不再修改最前面的 system 消息。相同索引不重复注入；
  删除全部索引时明确告知模型，读取失败则保留上次可用状态。
- 快照随会话保存、重载，模型请求投影时渲染；公开历史与用户原文不包含快照。
- token 估算计入快照，避免隐形上下文绕过压缩预算。

参考 zcode 的 provider-request-messages 和 context builder，以及 deepseek-harness 的
request reconstruction / request-cache 测试：动态状态在历史中保留发生位置，后续请求追加，
不反复改写前面的内容。它们不能保证不同供应商、不同工作负载都达到固定 97%。

## 真实 gpt-6-luna 结果

隔离配置和工作区，使用 LA 的 `runKBrainTurn` → KB → 真实上游。
同样的 8 轮提示词：计划更新、实际 Read 读取变化后的文件，再连续读取。
上游调用数量由真实模型决定；透明代理仅记录请求哈希和 usage，不保存 API key 或原文。
会话为独立运行，不保证首轮上游冷暖状态相同，以下是观察结果而非可归因的性能提升。

| 版本 | 主对话请求 | 输入 tokens | 命中 tokens | 总命中率 | 最后 5 请求 | 相邻请求消息前缀变化 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| Release v0.107.6-beta.1 | 21 | 177761 | 156672 | 88.14% | 95.07% | 5 |
| 计划/记忆快照修复 | 20 | 170200 | 133632 | 78.51% | 94.87% | 0 |
| 修复 + 显式会话亲和头 | 20 | 170216 | 141312 | 83.02% | 94.85% | 0 |

总命中率 = 上游 cached_tokens 之和 / input_tokens 之和，含首轮，未剔除零命中请求。
隐藏记忆提取使用不同工具与请求身份，上表只比较主对话，不代表所有后台流量的总比例。

修复版有 3 次零命中，亲和头实验有 2 次，旧版有 1 次；其中存在消息前缀、工具列表不变
但命中为 0 的续请求。非零返回值集中在 6656、7680、8704 等值。
这些观测不足以区分上游路由、缓存淘汰、缓存写入时机或供应商统计粒度，不能断言原因。
显式亲和头没有证明可以稳定解决问题，因此没有更改用户配置或默认启用该选项。

## 当前结论与边界

已消除复现工作负载中的客户端前缀破坏；尚未证明整体真实命中率提高，更没有达到稳定 97%。
保留缓存开关和现有统计口径，不填充无用 token，不延迟请求等待缓存，不冻结记忆内容。
旧版 markdown memory、用户修改系统提示词、切换工具集合、历史编辑和上下文压缩仍可能
合理改变前缀，不应以错误或过时上下文换取命中数字。

本次只提交 KB 源码，不发布未证明命中率提升的新二进制。LA 仍锁定已发布的
`v0.107.6-beta.1`，其测试和桌面打包继续直接下载 Release。
